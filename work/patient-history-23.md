# 23. 환자 임상 History

개발 구현과 9920 개발 서버 배포를 완료했다. 임상 사용자 검토와 명령표의 사용자 확인은 대기 중이다.

## 범위와 참조 자료

- **화면에서 확인**. PDF 25쪽의 History 화면은 과거 진단 보고서 목록과 선택한 기록의 본문을 같은 영역에 표시한다. [참조 PDF](../reference/Techcyte_IMS_Demo_Screen_Analysis.pdf)
- **발표 설명**. 발표자는 가상 Epic 테스트 환경에서 가져온 과거 진단·진료 기록을 확인하는 흐름을 설명했다.
- **참석자 의견**. 기관별 조회 권한, 기록 도착 지연 허용 범위와 원천 전환 정책에 대한 확정 의견은 기록에서 확인되지 않았다.
- **IMS 구현 결정**. 현재 앱의 케이스 접근과 환자 대조를 재사용한다. 병리의는 배정 케이스를 통해 연결된 환자 기록을 조회하며, 관리자와 해당 병리의만 수기 기록을 추가한다. 기관 권한으로 간호·접수·참관 역할에 확장하는 정책은 미확정이며 기관 승인이 필요하다. 기준 베이스 `d3741bc`를 확인했고 Canvas는 기존 뷰어를 사용한다.

## 동작과 계약

- **Case Details → History**는 환자 임상 기록과 기존 케이스 변경 감사 이력을 표시한다. **WSI Viewer → Patient History**는 같은 목록과 상세를 대화상자로 열어 현재 스캔·카메라를 유지한다.
- 로컬 환자를 연결한 후 **Add Clinical Record**에서 **Diagnostic Report** 또는 **Encounter Note**, 진료일, 제목, 본문을 저장한다. 수기 기록은 생성자와 입력 시각을 보존하며 기존 기록 수정 없이 새 기록을 추가한다. 동일 요청 재시도에는 `Idempotency-Key`를 사용한다. 수기 감사 이벤트에는 본문을 복제하지 않는다.
- 기록 목록·본문은 케이스로 범위를 제한한 `GET /api/clinical/{organization}/cases/{case_id}/patient-history`와 `GET .../document`에서 각각 조회한다. 목록의 외부 기록 키는 서버에서 원천 ID를 해시한 값이다. 브라우저의 목록과 주소에는 해시된 문서 키를 제공한다.
- 기존 `POST /api/integration/{organization}/connections/{channel}/messages`의 `resource: "history"`는 채널별 문서 ID인 `external_id`, 양의 정수 `revision`, 그리고 `data`의 `kind`, `occurred_on`, `title`, `body`, `patient_external_id`를 받는다. 공급 계약에서 `patient_external_id`는 EMR 환자 식별자다. LIS 발신자가 이 식별자를 제공할 수 있는 경우에 같은 연결을 사용한다. 문서가 MRN을 바꾸는 업데이트는 충돌로 보관된다. 기존 큐에서 중복, 역순과 재시도를 처리한다.
- **Patient Information**에서 운영자가 확인한 EMR 환자 연결에 한해 수신 기록을 표시한다. 이름이나 수기 등록한 MRN이 같아도 표시 조건이 되지 않는다. 외부 환자 정보가 충돌하면 해당 연결의 기록을 숨긴다. 외부 조회는 미리 수신해 저장한 문서를 기반으로 한다. 화면은 진료일, 기록/수신 시각, 환자별 마지막 수신, 소스 연결 확인 시각, 문서 개정판을 표시한다.
- 연결 미설정·비활성·타임아웃 중에도 수기 기록과 이미 수신한 문서를 읽을 수 있다. 환자 링크가 확인된 상태에서 기록이 아직 수신되지 않았으면 별도로 표시한다. 기관별 보존·시효 기준의 승인 전까지 출처와 시각을 표시하며, 임상 판단에 사용할 수 있는 기간을 자동 판정하지 않는다. 실제 원천 어댑터는 기관 테스트 인터페이스가 필요하다.

## 마이그레이션과 복구

- `0012_patient_history`는 `patient_history_records` 및 외부 스냅샷의 환자 조회 인덱스를 추가한다. 기존 케이스, 진료 감사 이력과 EMR·LIS 수신 내용은 유지된다.
- 이전 앱으로 돌아갈 때 DB를 백업하고 이번 버전에서 들어온 `history` 유형의 `queued`/`retry_wait` 수신 건을 먼저 처리한다. 어댑터가 중단돼 처리할 수 없으면 DB 운영자가 이전 버전에서 대상 메시지의 상태를 확인해 격리해야 한다. 개발 DB에서 `python -s -m alembic downgrade 0011_viewer_preferences`를 실행하면 수기 기록 테이블과 추가 인덱스가 제거된다. 수기 기록을 복구하려면 백업이 필요하고, 수신 스냅샷과 기존 inbox는 보존된다.

## 검증

- Linux/Node 22.12.0/PostgreSQL 18.6/Chrome 146 및 합성 환자·진료 기록을 사용했다.
- 격리 DB `0011 → 0012 → 0011 → 0012`와 Alembic 스키마 일치, 기존 케이스와 설정 보존을 검증했다.
- `MEDIAUTO_DEMO_PORT=19923 scripts/verify-integration.sh` **PASS**. Playwright와 Tesseract 경로를 지정해 프런트 빌드, Alembic 검사, PostgreSQL/API 테스트 24개와 Chrome 시나리오 10개를 통과했다. 합성 기록으로 환자 대조 전 숨김, 타임아웃 중 수기·수신 기록 조회, 미수신 상태, 배정/기관 권한, 수기 재시도 중복 방지, 두 형식의 본문, 뷰어 복귀 후 줌 유지까지 확인했다.
- 9920 개발 서버에서 `.runtime/before-history-0012-20261124T174125.dump` 백업을 확인하고 마이그레이션을 적용했다. 이전 케이스·환자·스냅샷·설정 등의 건수와 설정 지문을 비교했으며, 로그인·Worklist·History 엔드포인트를 확인했다. 등록 임상 케이스가 없는 개발 서버에서는 실제 화면 검증에 격리 브라우저 테스트의 합성 케이스를 사용했다.
- 기관 실제 EMR·LIS 접속과 임상 사용자 확인은 대기 중이다.
